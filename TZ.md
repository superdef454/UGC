# ТЗ: опросы UGC

Исходное задание - в pdf рядом. Коротко, что требуют:

Обязательно:
- Django + DRF
- модели: пользователи, опросы, вопросы, варианты ответов, прохождения, ответы, статистика
- порядок вопросов и вариантов задаёт автор, должна быть возможность ввести свой ответ
- view, которая отдаёт следующий вопрос с учётом прогресса
- PostgreSQL

Будет плюсом: фронт (templates или React), тесты, docker-compose, ASGI / оптимизации под нагрузку (можно в комментариях).

Не нужно: прод-стенд, полноценная авторизация (хватит идентификации пользователя).


## Что делаю

Основной сценарий целиком: создал опрос -> опубликовал -> прошли -> автор смотрит статистику.
Остальное оставляю TODO в коде.

Функции:
1. создать опрос сразу с вопросами и вариантами (создаётся черновиком)
2. поменять порядок вопросов и вариантов (пока черновик)
3. опубликовать / закрыть опрос
4. список доступных опросов, список своих опросов
5. пройти опрос: получить следующий вопрос, ответить (в ответе сразу приходит следующий вопрос)
6. продолжить прохождение - прогресс хранится на сервере, можно вернуться позже
7. статистика по своему опросу

## Правила

Опрос:
- статусы: черновик -> опубликован -> закрыт
- менять можно только черновик, после публикации структура замораживается
- для публикации нужен хотя бы один вопрос, у каждого вопроса есть варианты или разрешён свой ответ
- создать опрос может любой залогиненный, всё остальное с опросом - только автор

Прохождение:
- проходить можно только опубликованный опрос
- один пользователь - одно прохождение, повторно нельзя
- прохождение создаётся при первом запросе следующего вопроса
- следующий вопрос = первый по порядку, на который ещё нет ответа
- отвечать можно только на текущий вопрос, перескакивать нельзя
- одиночный выбор: один вариант или свой ответ; множественный: варианты и/или свой ответ
- свой ответ - только если у вопроса он разрешён
- необязательный вопрос можно пропустить (пустой ответ), обязательный нельзя
- после последнего ответа прохождение завершается и уходит в очередь на статистику
- в закрытом опросе ответить уже нельзя

Время ставит сервер: started_at у прохождения и answered_at у ответа. Фронту тут не доверяю.
Время на вопрос = answered_at минус answered_at предыдущего ответа (для первого - минус started_at).

Статистика:
- сколько раз прошли до конца
- сколько ответили / пропустили каждый вопрос
- популярные ответы (счётчики по вариантам + сколько написали свой)
- среднее время прохождения
- среднее время на вопрос, над каким думали дольше всего


## Нагрузка

Из задания: ~1M опросов, ~15 вопросов, ~5 вариантов, ~15M пользователей, каждый проходит ~5 опросов.

Отсюда:
- вопросов ~15M, вариантов ~75M
- прохождений 15M * 5 = ~75M
- ответов 75M * 15 = ~1.1 млрд - вот где вся нагрузка

RPS в задании нет, период не указан. Считаю, что объём набирается за год:
- ~32 запроса на прохождение -> ~2.4 млрд запросов в год -> ~75 rps в среднем
- днём x3, всплески (рассылки, вирусный опрос) x5-10 -> закладываюсь на 1-2k rps в пике
- если ответ сразу возвращает следующий вопрос, запросов на прохождение ~17 вместо 32

## Модели

Все PK - BigAutoField, на объёме ответов int32 кончится.

users.User - AbstractUser без своих полей

quizzes.Quiz
- author FK User (PROTECT)
- title, description
- status: draft / published / closed (TODO: on_moderation)
- cloned_from FK self, null
- created_at, updated_at, published_at
- индексы: (author, -created_at) для "мои опросы"; частичный (-published_at, -id) where status = published для списка доступных

quizzes.Question
- quiz FK (CASCADE)
- text, type (single / multiple), order
- allow_custom_answer, is_required
- unique (quiz, order) deferrable - чтобы менять порядок в одной транзакции

quizzes.AnswerOption
- question FK (CASCADE), text, order
- unique (question, order) deferrable

attempts.Attempt
- user FK, quiz FK (PROTECT - опрос с прохождениями не удалить)
- status: in_progress / finished
- started_at, finished_at
- unique (user, quiz) - он же покрывает "мои прохождения"
- check: finished_at заполнен только у finished

attempts.Answer
- attempt FK, question FK
- selected_options M2M через AnswerChoice
- custom_text, answered_at
- unique (attempt, question) - один ответ на вопрос, заодно защита от двойной отправки

attempts.AnswerChoice - явная through-модель для M2M (у автоматической таблицы id не BigAutoField и индексы не под контролем)
- answer FK, option FK
- unique (answer, option)

У FK, которые уже покрыты составным уникальным индексом, свой индекс отключаю (db_index=False). На миллиарде строк лишний индекс - это десятки гигабайт.

analytics.QuizStatistics - готовая статистика, пишет только воркер
- quiz O2O (pk)
- attempts_count, total_duration_ms - колонки, по ним можно сортировать
- data - json по вопросам и вариантам, схема на pydantic
- индекс по -attempts_count

analytics.StatisticsOutbox - очередь на подсчёт
- attempt O2O, created_at


## Статистика через outbox

1. при завершении прохождения в той же транзакции кладу запись в StatisticsOutbox
2. воркер (management command, отдельный сервис в compose) раз в пару секунд берёт пачку через select_for_update(skip_locked=True)
3. в одной транзакции: считает дельты по пачке, лочит строки QuizStatistics по порядку quiz_id (чтобы воркеры не ловили дедлоки), прибавляет, удаляет пачку из очереди
4. упал воркер - транзакция откатилась, записи остались в очереди, посчитаются один раз

Считаю только суммы и счётчики, их можно складывать пачками. Медиану так не посчитать, это уже не сюда.
