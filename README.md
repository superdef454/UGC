# UGC-опросы

Тестовое задание: пользовательские опросы. Одни пользователи создают опросы и смотрят по ним статистику, другие проходят. Исходное задание - `Опросы_UGC(тз).pdf`, мой разбор требований - [TZ.md](TZ.md).

Главное, что просили в задании:
- модели - [quizzes/models.py](quizzes/models.py), [attempts/models.py](attempts/models.py), [analytics/models.py](analytics/models.py)
- view со следующим вопросом для опроса id = NNN - `GET /api/quizzes/NNN/next-question/`, код в [attempts/views.py](attempts/views.py) и [attempts/services.py](attempts/services.py)


## Запуск

```bash
docker compose up --build
docker compose exec web python manage.py seed_demo
```

Дальше http://localhost:8080, вход `alice` / `demo-pass` (автор опроса «Овощи» с готовой статистикой) или `bob` / `demo-pass` (может его пройти).
Swagger - http://localhost:8080/api/docs/, в Authorize можно указать `X-User-Id` (у alice id=1, у bob id=2).

В compose поднимаются: postgres, миграции, web (gunicorn + uvicorn-воркеры), воркер статистики и nginx. Если порты заняты: `APP_PORT=8088 POSTGRES_PORT=5433 docker compose up`.

## Что сделано

Основной сценарий целиком:
1. автор собирает опрос в конструкторе - вопросы, варианты, порядок, можно ли свой ответ, обязательный ли вопрос
2. публикует (после этого структура заморожена)
3. участник проходит по одному вопросу, может бросить и продолжить позже
4. после последнего ответа прохождение уходит в очередь, воркер через пару секунд обновляет статистику
5. автор смотрит статистику: сколько прошли, среднее время, популярные ответы, свои ответы, над каким вопросом думали дольше всего

Всё это есть и в API, и на страницах (шаблоны Django). Остальное, что не входит в основной сценарий, оставил TODO в коде (см. ниже).


## Как устроено

Приложения:
- `users` - своя модель пользователя и временная аутентификация по `X-User-Id`
- `quizzes` - опросы, вопросы, варианты, публикация, порядок
- `attempts` - прохождения, ответы, логика следующего вопроса
- `analytics` - статистика, очередь (outbox) и воркер
- `moderation` - заглушка `check_text()`, через неё уже проходят все тексты
- `web` - страницы

Бизнес-логика в `services.py`, view тонкие. Ошибки бизнес-правил - `DomainError`, API отдаёт их как 400/403/404 с понятным текстом.

### Модели

```
User ─< Quiz ─< Question ─< AnswerOption
  │       │         │            │
  └─< Attempt ─< Answer ─< AnswerChoice
          │
          └── StatisticsOutbox        Quiz ── QuizStatistics
```

- Порядок - поле `order` с уникальностью `(quiz, order)` / `(question, order)`. Ограничения отложенные (`DEFERRABLE INITIALLY DEFERRED`), поэтому перестановка - один `bulk_update` в транзакции без танцев с временными значениями.
- Одно прохождение на пару пользователь + опрос (`unique(user, quiz)`), один ответ на вопрос (`unique(attempt, question)`) - это же защита от двойной отправки.
- Множественный выбор - через явную through-модель `AnswerChoice`, свой ответ - `Answer.custom_text`. Пустой ответ на необязательный вопрос = пропуск.
- Все PK - `BigAutoField`: ответов будет больше 2 млрд за пару лет.
- У FK, которые уже покрыты составным уникальным индексом, свой индекс выключен (`db_index=False`). На таблице в миллиард строк лишний индекс - это десятки гигабайт.

### Следующий вопрос

Следующий вопрос = первый по порядку, на который ещё нет ответа. Структура опубликованного опроса не меняется, поэтому она кэшируется ([quizzes/structure.py](quizzes/structure.py)), и на каждый запрос в базу идёт только один index-only запрос за id отвеченных вопросов. Ответ на вопрос сразу возвращает следующий, так что на прохождение уходит ~17 запросов вместо ~32.

Запись ответа лочит только строку прохождения (`select_for_update(of=("self",))`), не опрос - иначе все, кто проходит популярный опрос, стояли бы в очереди на одну строку.

### Статистика

Считается не при запросе, а заранее, через outbox:
1. при завершении прохождения в той же транзакции пишется строка в `StatisticsOutbox`
2. воркер (`manage.py process_statistics`) раз в пару секунд берёт пачку через `select_for_update(skip_locked=True)`, считает прирост, прибавляет к `QuizStatistics` и удаляет пачку из очереди - всё одной транзакцией
3. упал посередине - откат, пачка осталась в очереди, ничего не потерялось и не задвоилось. Воркеров можно запустить несколько, `SKIP LOCKED` разведёт их по разным пачкам, а строки статистики лочатся по порядку `quiz_id`, чтобы не было дедлоков

`QuizStatistics` - это готовая read-модель: счётчики для сортировки в колонках, детализация по вопросам и вариантам в json со схемой на pydantic ([analytics/schemas.py](analytics/schemas.py)). Хранятся только суммы и счётчики, средние считаются при чтении.

Время на вопрос = `answered_at` ответа минус `answered_at` предыдущего (для первого - минус `started_at`). Время ставит сервер, клиенту тут не доверяю.

### ASGI и async

Запускается под ASGI (gunicorn + uvicorn-воркеры). Горячий путь - список опросов, следующий вопрос, ответ, статистика - async view (через `adrf`, в самом DRF async нет) и async ORM. Всё, где нужна транзакция, - обычные синхронные сервисы через `sync_to_async`: транзакции в async ORM Django пока не поддерживает. Редкие действия автора (создание, публикация) - обычные sync view.

Для async пришлось выключить постоянные соединения (`CONN_MAX_AGE = 0`), вместо них пул psycopg 3.


## Почему так, а не иначе

**Ответы в нормальных таблицах, а не json в прохождении.** Был соблазн: опубликованный опрос не меняется, строк было бы ~75M вместо ~1.1 млрд. Но ответы приходят по одному, и json перезаписывался бы 15 раз за прохождение (`UPDATE` в Postgres - это новая версия всей строки, плюс работа для VACUUM). База не проверяет id вариантов внутри json, экономия места выходит раза в два, а не в 15, а аналитические запросы по json на 75M строк - боль. Миллиард строк для Postgres с нормальными индексами и партициями - рабочий объём.

**Статистика - наоборот json.** Это производные данные: читаются целиком, пишутся одним воркером, при поломке пересчитываются из ответов. Нормализовать их смысла нет, а то, по чему нужна сортировка, вынесено в колонки.

**Outbox, а не счётчики при ответе и не Celery на каждый ответ.** Синхронный `count + 1` у вирусного опроса упирается в блокировку одной строки. `.delay()` на каждый ответ теряет события при падении брокера или считает лишнее, если транзакция откатилась. Outbox в той же транзакции даёт учёт ровно один раз и не требует брокера.

**Опубликованный опрос нельзя редактировать.** Иначе статистика и уже данные ответы перестают сходиться со структурой. Правильный путь - клон в новый черновик (TODO).


## Нагрузка

Из задания: ~1M опросов, ~15 вопросов, ~5 вариантов, ~15M пользователей, каждый проходит ~5 опросов. Это ~75M прохождений и ~1.1 млрд ответов.

RPS в задании нет, считал так: если объём набирается за год, это ~2.4 млрд запросов, ~75 rps в среднем, с учётом суток и всплесков - 1-2k rps в пике. Для такого хватает текущей схемы: индексы под каждый запрос, курсорная пагинация, кэш структуры опроса, статистика без агрегаций на чтении, пул соединений.

Что дальше при росте:
- PgBouncer перед базой, Redis вместо локального кэша
- партиционирование `Answer` / `AnswerChoice` (по хэшу `attempt_id` или по времени)
- реплика для чтения статистики
- сырые ответы и аналитика - в ClickHouse через Kafka, Postgres оставить для прохождений


## API

| Метод | Путь | Что делает |
|---|---|---|
| GET | `/api/quizzes/` | опубликованные опросы |
| GET | `/api/quizzes/{id}/next-question/` | следующий вопрос и прогресс (при первом запросе начинает прохождение) |
| POST | `/api/quizzes/{id}/answers/` | ответ на текущий вопрос, в ответе - следующий |
| GET | `/api/attempts/?status=in_progress` | мои прохождения |
| GET, POST | `/api/my/quizzes/` | мои опросы / создать опрос целиком |
| GET | `/api/my/quizzes/{id}/` | мой опрос со структурой |
| POST | `/api/my/quizzes/{id}/publish/`, `/close/` | опубликовать / закрыть |
| POST | `/api/my/quizzes/{id}/questions/order/` | порядок вопросов `{"ids": [...]}` |
| POST | `/api/my/questions/{id}/options/order/` | порядок вариантов |
| GET | `/api/my/quizzes/{id}/statistics/` | статистика |

Подробно со схемами - в swagger.
