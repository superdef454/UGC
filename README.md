## Запуск

```bash
docker compose up --build
docker compose exec web python manage.py seed_demo
```

- сайт - http://localhost:8080, пользователи `alice` (автор опроса «Овощи» с заполненной статистикой) и `bob`, пароль `demo-pass`
- swagger - http://localhost:8080/api/docs/, в Authorize указывается `X-User-Id` (alice - 1, bob - 2)

Compose поднимает postgres, миграции и сборку статики, web (gunicorn + uvicorn-воркеры), воркер статистики и nginx. Порты на хосте: сайт 8080, база 5444 только на localhost. Переопределяются через `APP_PORT` и `DB_HOST_PORT`, для локального запуска Django тот же порт базы передаётся в `POSTGRES_PORT`.

Compose - демо-стенд, не прод: идентификация по `X-User-Id` включена, секреты и пароль базы заданы прямо в файле.

## Объём реализации

Основной сценарий целиком, в API и на страницах (шаблоны Django):
1. автор собирает опрос: вопросы, варианты, порядок, разрешён ли свой ответ, обязателен ли вопрос
2. публикует - после этого структура заморожена
3. участник начинает прохождение и отвечает по одному вопросу, может прерваться и продолжить позже
4. после последнего ответа прохождение попадает в очередь, воркер за пару секунд обновляет статистику
5. автор смотрит статистику: число прохождений, среднее время, популярные ответы, свои ответы, самый долгий вопрос

Всё, что за рамками основного сценария, отмечено TODO в коде и перечислено в конце.


## API

Базовый путь - `/api/v1/`. Пользователь определяется по сессии (сайт) или по заголовку `X-User-Id` (временная идентификация, см. TODO). Списки - курсорная пагинация (`next` / `previous`).

| Метод | Путь | Назначение | Коды |
|---|---|---|---|
| GET | `/quizzes/` | каталог опубликованных опросов | 200 |
| GET | `/quizzes/?author=me[&status=draft]` | опросы текущего пользователя в любом статусе | 200, 400 |
| POST | `/quizzes/` | создать черновик целиком, с вопросами и вариантами | 201, 400 |
| GET | `/quizzes/{quiz_id}/` | опрос со структурой; черновик виден только автору | 200, 404 |
| POST | `/quizzes/{quiz_id}/publish/` | опубликовать черновик | 200, 400, 404, 409 |
| POST | `/quizzes/{quiz_id}/close/` | закрыть опрос | 200, 404, 409 |
| PUT | `/quizzes/{quiz_id}/questions/order/` | порядок вопросов: `{"ids": [...]}` | 204, 400, 404, 409 |
| PUT | `/quizzes/{quiz_id}/questions/{question_id}/options/order/` | порядок вариантов | 204, 400, 404, 409 |
| GET | `/quizzes/{quiz_id}/statistics/` | статистика, только автору | 200, 404 |
| POST | `/quizzes/{quiz_id}/attempt/` | начать прохождение; если уже начато - вернуть его | 201, 200, 404, 409 |
| GET | `/quizzes/{quiz_id}/attempt/` | прохождение: прогресс и `next_question` | 200, 404 |
| POST | `/quizzes/{quiz_id}/attempt/answers/` | ответ на текущий вопрос | 200, 400, 404, 409 |
| GET | `/attempts/?status=in_progress` | прохождения текущего пользователя | 200 |

Смысл кодов ошибок, тело всегда `{"detail": "..."}`:
- 400 - невалидные данные или нарушено правило (обязательный вопрос без ответа, два варианта в одиночном выборе)
- 404 - нет такого объекта или он недоступен. Чужой опрос тоже 404, а не 403, чтобы по коду ответа нельзя было перебирать чужие черновики
- 409 - действие не подходит текущему состоянию: опрос закрыт, уже пройден, ответ не на текущий вопрос, повторная публикация

Прохождение - подресурс опроса в единственном числе (`/attempt/`): на пару пользователь + опрос оно одно, это гарантирует уникальный индекс. GET безопасен и ничего не создаёт, начало прохождения - явный POST. Порядок задаётся через PUT: присылается полный список id, операция идемпотентна.

Пример прохождения:

```bash
curl -X POST -H "X-User-Id: 2" localhost:8080/api/v1/quizzes/1/attempt/
# 201 {"id": 41, "status": "in_progress", "progress": {"answered": 0, "total": 5, ...},
#      "next_question": {"id": 1, "text": "Ты любишь буратту с помидорами?", "options": [...]}}

curl -X POST -H "X-User-Id: 2" -H "Content-Type: application/json" \
     -d '{"question_id": 1, "option_ids": [2]}' localhost:8080/api/v1/quizzes/1/attempt/answers/
# 200 {..., "progress": {"answered": 1, ...}, "next_question": {"id": 2, ...}}
```

Ответ сразу возвращает следующий вопрос, поэтому прохождение из 15 вопросов - это ~17 запросов, а не ~32.


## Устройство

Приложения:
- `users` - модель пользователя, идентификация по `X-User-Id`
- `quizzes` - опросы, вопросы, варианты, публикация, порядок
- `attempts` - прохождения, ответы, логика следующего вопроса
- `analytics` - статистика, очередь (outbox) и воркер
- `moderation` - точка расширения `check_text()`, через неё проходят все пользовательские тексты
- `web` - страницы

Бизнес-логика - в `services.py`, view тонкие. Нарушения бизнес-правил - исключения из `core/exceptions.py`, обработчик DRF превращает их в 400 / 404 / 409.

### Модели

```
User ─< Quiz ─< Question ─< AnswerOption
  │       │         │            │
  └─< Attempt ─< Answer ─< AnswerChoice
          │
          └── StatisticsOutbox        Quiz ── QuizStatistics
```

- Порядок - поле `order` с уникальностью `(quiz, order)` / `(question, order)`. Ограничения отложенные (`DEFERRABLE INITIALLY DEFERRED`), поэтому перестановка - один `bulk_update` в транзакции без промежуточных значений.
- Одно прохождение на пару пользователь + опрос (`unique(user, quiz)`), один ответ на вопрос (`unique(attempt, question)`) - заодно защита от двойной отправки.
- Множественный выбор - явная through-модель `AnswerChoice`, свой ответ - `Answer.custom_text`. Пустой ответ на необязательный вопрос - пропуск.
- Все PK - `BigAutoField`: ответов на целевых объёмах больше 2 млрд за пару лет.
- У FK, покрытых составным уникальным индексом, собственный индекс выключен (`db_index=False`): на таблице в миллиард строк лишний индекс - десятки гигабайт. Индексы `Answer.question` и `AnswerChoice.option` оставлены осознанно - без них проверка `PROTECT` при удалении вопроса из черновика превращается в seq scan.
- Опубликованный опрос заморожен и в админке: структура и статус там только для просмотра.

### Следующий вопрос

Следующий вопрос - первый по порядку, на который ещё нет ответа. Структура опубликованного опроса не меняется и кэшируется ([quizzes/structure.py](quizzes/structure.py)), поэтому на запрос в базу уходит один index-only запрос за id отвеченных вопросов.

Запись ответа блокирует только строку прохождения (`select_for_update(of=("self",))`), не опрос: иначе все участники популярного опроса выстраивались бы в очередь на одну строку.

### Статистика

Считается заранее, через outbox, а не при запросе:
1. при завершении прохождения в той же транзакции пишется строка в `StatisticsOutbox`
2. воркер (`manage.py process_statistics`) раз в пару секунд берёт пачку через `select_for_update(skip_locked=True)`, считает прирост, прибавляет к `QuizStatistics` и удаляет пачку из очереди - одной транзакцией
3. при сбое транзакция откатывается и пачка остаётся в очереди - ничего не теряется и не учитывается дважды. Воркеров может быть несколько: `SKIP LOCKED` разводит их по разным пачкам, а строки статистики блокируются в порядке `quiz_id`, что исключает взаимные блокировки. Ошибка в пачке не роняет воркер: повтор с нарастающей паузой

`QuizStatistics` - готовая read-модель: счётчики для сортировки в колонках, детализация по вопросам и вариантам в json со схемой на pydantic ([analytics/schemas.py](analytics/schemas.py)). Хранятся только суммы и счётчики, средние считаются при чтении.

Время на вопрос - `answered_at` ответа минус `answered_at` предыдущего (для первого - минус `started_at`). Время ставит сервер, клиентскому времени доверять нельзя. Прохождение можно прервать на сутки, поэтому вклад одного вопроса ограничен 10 минутами, а время прохождения - сумма времени по вопросам: иначе одна пауза искажает все средние.

### ASGI и async

Сервис работает под ASGI (gunicorn + uvicorn-воркеры). Горячий путь - каталог, прохождение, ответ, статистика - async view (`adrf`, в самом DRF async нет) и async ORM. Всё, где нужна транзакция, - синхронные сервисы через `sync_to_async`: транзакции в async ORM Django не поддерживает. Редкие действия автора - обычные sync view.

Постоянные соединения в async-режиме выключены (`CONN_MAX_AGE = 0`), вместо них пул psycopg 3.

Ограничение: async ORM в Django - обёртка над синхронным кодом, обращения к базе внутри процесса идут через один поток (`sync_to_async(thread_sensitive=True)`). Пропускную способность к базе async сам по себе не увеличивает - она масштабируется процессами (`WEB_CONCURRENCY`) и инстансами. Выигрыш ASGI появляется на внешнем I/O: Redis, HTTP-вызовы, внешняя модерация.


## Принятые решения

**Ответы в нормализованных таблицах, а не json в прохождении.** Опубликованный опрос не меняется, и json дал бы ~75M строк вместо ~1.1 млрд. Но ответы приходят по одному, и json перезаписывался бы 15 раз за прохождение (`UPDATE` в Postgres создаёт новую версию всей строки, плюс нагрузка на VACUUM). База не проверяет id вариантов внутри json, экономия места - примерно в два раза, а не в 15, а аналитические запросы по json на 75M строк медленные. Миллиард строк для Postgres с правильными индексами и партициями - рабочий объём.

**Статистика, наоборот, в json.** Это производные данные: читаются целиком, пишутся одним воркером, при поломке пересчитываются из ответов. Поля для сортировки вынесены в колонки.

**Outbox вместо синхронных счётчиков и Celery на каждый ответ.** Синхронный `count + 1` у вирусного опроса упирается в блокировку одной строки. `.delay()` на каждый ответ теряет события при падении брокера и учитывает лишнее при откате транзакции. Outbox в той же транзакции даёт учёт ровно один раз без брокера.

**Опубликованный опрос не редактируется.** Иначе статистика и данные ответы перестают соответствовать структуре. Изменение опубликованного опроса - через клон в новый черновик (TODO).


## Нагрузка

Из задания: ~1M опросов, ~15 вопросов, ~5 вариантов, ~15M пользователей, каждый проходит ~5 опросов - это ~75M прохождений и ~1.1 млрд ответов.

RPS в задании не указан. Если объём набирается за год, это ~2.4 млрд запросов, ~75 rps в среднем и 1-2k rps в пике с учётом суточного цикла и всплесков. Под этот расчёт: индексы под каждый запрос, курсорная пагинация, кэш структуры опроса, статистика без агрегаций на чтении, пул соединений.

Замер на ноутбуке (docker compose, 4 процесса web, 3 воркера статистики): 300 одновременных прохождений - ~470 rps, p95 ~155 мс, без ошибок. При параллельной отправке каждого ответа пятью запросами в базе остаётся ровно один ответ на вопрос, статистика совпадает с прямым пересчётом по сырым ответам. До 1-2k rps - горизонтально: больше процессов и инстансов web, PgBouncer.

Дальнейшее масштабирование:
- PgBouncer перед базой, Redis вместо локального кэша
- партиционирование `Answer` / `AnswerChoice` по хэшу `attempt_id` или по времени
- реплика для чтения статистики
- сырые ответы и аналитика - в ClickHouse через Kafka, Postgres - для прохождений
