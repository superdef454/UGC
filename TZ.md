# ТЗ: опросы UGC

Исходное задание - pdf в корне репозитория. Требования из него:

Обязательно:
- Django + DRF
- модели: пользователи, опросы, вопросы, варианты ответов, прохождения, ответы, статистика
- порядок вопросов и вариантов задаёт автор, должна быть возможность ввести свой ответ
- view, которая отдаёт следующий вопрос с учётом прогресса
- PostgreSQL

Будет плюсом: фронт (templates или React), тесты, docker-compose, ASGI / оптимизации под нагрузку (можно в комментариях).

Не требуется: прод-стенд, полноценная авторизация (достаточно идентификации пользователя).


## Объём работ

Основной сценарий целиком: создание опроса -> публикация -> прохождение -> статистика для автора.
Остальное - TODO в коде.

Функции:
1. создание опроса сразу с вопросами и вариантами (создаётся черновиком)
2. изменение порядка вопросов и вариантов (пока опрос черновик)
3. публикация и закрытие опроса
4. каталог опубликованных опросов, список опросов автора
5. прохождение: явный старт, следующий вопрос, ответ (ответ сразу возвращает следующий вопрос)
6. продолжение прохождения - прогресс хранится на сервере
7. статистика по опросу для автора

## Правила

Опрос:
- статусы: черновик -> опубликован -> закрыт
- менять можно только черновик, после публикации структура замораживается (в том числе в админке)
- для публикации нужен хотя бы один вопрос, у каждого вопроса есть варианты или разрешён свой ответ
- создать опрос может любой идентифицированный пользователь, остальные действия с опросом - только автор
- черновик виден только автору, для остальных - 404

Прохождение:
- начать можно только опубликованный опрос
- одно прохождение на пару пользователь + опрос, повторно пройти нельзя
- прохождение начинается явным действием (POST), просмотр ничего не создаёт
- следующий вопрос - первый по порядку, на который ещё нет ответа
- ответить можно только на текущий вопрос, перескакивать нельзя
- одиночный выбор: один вариант или свой ответ; множественный: варианты и/или свой ответ
- свой ответ - только если у вопроса он разрешён
- необязательный вопрос можно пропустить (пустой ответ), обязательный нельзя
- после последнего ответа прохождение завершается и попадает в очередь на статистику
- в закрытом опросе новые прохождения и ответы запрещены

Время ставит сервер: `started_at` у прохождения и `answered_at` у ответа, клиентскому времени доверять нельзя.
Время на вопрос - `answered_at` минус `answered_at` предыдущего ответа (для первого - минус `started_at`), но не больше 10 минут: прохождение можно прервать на сутки, и без ограничения одна пауза искажает средние. Время прохождения - сумма времени по вопросам.

Статистика:
- число завершённых прохождений
- сколько ответили / пропустили каждый вопрос
- популярные ответы (счётчики по вариантам + число своих ответов)
- среднее время прохождения
- среднее время на вопрос, самый долгий вопрос


## Нагрузка

Из задания: ~1M опросов, ~15 вопросов, ~5 вариантов, ~15M пользователей, каждый проходит ~5 опросов.

Производные объёмы:
- вопросов ~15M, вариантов ~75M
- прохождений 15M * 5 = ~75M
- ответов 75M * 15 = ~1.1 млрд - основная нагрузка

RPS и период в задании не указаны. Допущение - объём набирается за год:
- ~32 запроса на прохождение -> ~2.4 млрд запросов в год -> ~75 rps в среднем
- днём x3, всплески (рассылки, вирусный опрос) x5-10 -> ориентир 1-2k rps в пике
- ответ сразу возвращает следующий вопрос -> ~17 запросов на прохождение вместо 32


## Стек

- adrf для async view (в самом DRF async нет)
- ASGI: gunicorn + uvicorn worker
- PostgreSQL 16, psycopg 3 с пулом соединений (`CONN_MAX_AGE = 0` - требование async-режима)

Идентификация:
- своя модель User (без своих полей, но заведена сразу)
- сайт: LoginView + сессии
- API и тесты: заголовок `X-User-Id`, включается флагом (dev и демо-compose), в проде выключен. TODO: токены / OAuth


## API

`/api/v1/`, ресурсы без привязки к текущему пользователю в пути:
- `/quizzes/` - каталог (GET), создание (POST); `?author=me` - опросы текущего пользователя
- `/quizzes/{quiz_id}/` - опрос; `/publish/`, `/close/` - переходы статуса
- `/quizzes/{quiz_id}/questions/order/`, `/quizzes/{quiz_id}/questions/{question_id}/options/order/` - порядок (PUT, полный список id)
- `/quizzes/{quiz_id}/statistics/` - статистика автора
- `/quizzes/{quiz_id}/attempt/` - прохождение текущего пользователя (POST - начать, GET - прогресс и `next_question`)
- `/quizzes/{quiz_id}/attempt/answers/` - ответ на текущий вопрос
- `/attempts/` - прохождения текущего пользователя

Ошибки - `{"detail": "..."}`: 400 - невалидные данные, 404 - не найдено или недоступно, 409 - конфликт состояния (опрос закрыт, уже пройден, не текущий вопрос).


## Модели

Все PK - BigAutoField: на объёме ответов int32 не хватит.

users.User - AbstractUser без своих полей

quizzes.Quiz
- author FK User (PROTECT)
- title, description
- status: draft / published / closed (TODO: on_moderation)
- cloned_from FK self, null
- created_at, updated_at, published_at
- индексы: (author, -created_at) для опросов автора; частичный (-published_at, -id) where status = published для каталога

quizzes.Question
- quiz FK (CASCADE)
- text, type (single / multiple), order
- allow_custom_answer, is_required
- unique (quiz, order) deferrable - перестановка в одной транзакции

quizzes.AnswerOption
- question FK (CASCADE), text, order
- unique (question, order) deferrable

attempts.Attempt
- user FK, quiz FK (PROTECT - опрос с прохождениями не удалить)
- status: in_progress / finished
- started_at, finished_at
- unique (user, quiz) - покрывает и список прохождений пользователя
- check: finished_at заполнен только у finished

attempts.Answer
- attempt FK, question FK
- selected_options M2M через AnswerChoice
- custom_text, answered_at
- unique (attempt, question) - один ответ на вопрос, защита от двойной отправки

attempts.AnswerChoice - явная through-модель для M2M (у автоматической таблицы тип PK и индексы не под контролем)
- answer FK, option FK
- unique (answer, option)

У FK, покрытых составным уникальным индексом, собственный индекс отключён (`db_index=False`): на миллиарде строк лишний индекс - десятки гигабайт.

analytics.QuizStatistics - готовая статистика, пишет только воркер
- quiz O2O (pk)
- attempts_count, total_duration_ms - колонки для сортировки
- data - json по вопросам и вариантам, схема на pydantic
- индекс по -attempts_count

analytics.StatisticsOutbox - очередь на подсчёт
- attempt O2O, created_at


## Статистика через outbox

1. при завершении прохождения в той же транзакции создаётся запись в StatisticsOutbox
2. воркер (management command, отдельный сервис в compose) раз в пару секунд берёт пачку через `select_for_update(skip_locked=True)`
3. в одной транзакции: дельты по пачке, блокировка строк QuizStatistics в порядке quiz_id (без взаимных блокировок между воркерами), прибавление, удаление пачки из очереди
4. при сбое транзакция откатывается, записи остаются в очереди и учитываются ровно один раз; ошибка не роняет воркер - повтор с нарастающей паузой

Хранятся только суммы и счётчики - их можно складывать пачками. Медиана так не считается, это за рамками задачи.
